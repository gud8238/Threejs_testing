# A안(2.5D) 평가 리포트 — 실패 분석

- 작성일: 2026-11-17
- 결과물: `renders/tiger_chase_A_720p.mp4` (1280×720, 30fps, 10.0초, 무음)
- 증거 프레임: `docs/review/A_failures.jpg`
- 샷별 스냅샷: `docs/review/03_shots.jpg`
- 범위 변경: 오디오(TTS 대사, Lyria BGM)는 사용자 결정으로 제외했다. 이번 테스트의 대상은 Three.js다.

---

## 1. 한 줄 결론

**A안의 실패 대부분은 Three.js가 아니라 "2D 이미지에는 3D 정보가 없다"는 데서 나왔다.** 렌더링 파이프라인(결정적 프레임 렌더, 깊이 패럴랙스, 후보정, 카메라 타임라인, 정지 연출)은 계획대로 동작했다. 반면 캐릭터 움직임은 기획 단계에서 예측한 ★★ 수준에 머물렀다.

따라서 이번 결과는 **"Three.js의 품질 상한"이 아니라 "2D 입력 에셋의 상한"을 잰 것**이다. Three.js 자체의 3D 캐릭터 표현력은 B2안에서 측정해야 한다.

## 2. 측정치

| 항목 | 값 |

| 사람 손이 간 보정 | 지면 깊이 곡선, 깊이 → 거리 변환식, 캐릭터 크기, 샷별 카메라 시선, 배경 가장자리 확장 |

## 3. 잘 된 것 (실패 판단의 기준선)

- **배경 패럴랙스:** 그림 한 장이 깊이 메시가 되어, 카메라가 움직이면 덤불·산길·원경이 서로 다른 속도로 움직인다. 정지 화면만 보면 원본 키아트와 거의 같은 룩이다.
- **차폐:** 호랑이가 덤불 뒤에서 몸 일부가 가려진 채 나온다 (3.6초).
- **후보정과 연출:** 블룸, 노을 그레이드, 비네트, 그레인, 9.3초 정지·탈색·플래시, 9.7초 암전이 모두 타임라인으로 제어되고, 매번 같은 결과가 나온다.
- **HyperFrames와 Three.js 연동:** `hf-seek` 이벤트 → GSAP 타임라인 이동 → 렌더 구조가 문제없이 동작했다. 영상용 Three.js의 기본기는 확보됐다.

## 4. 실패 목록

"예상"은 기획 단계(접근 방식 비교표)에서 미리 경고했는지를 뜻한다.

### F1. 달리기가 달리기로 보이지 않는다 (할머니) — 심각도: 높음
- **현상:** 포즈 g_2와 g_3를 초당 9번 번갈아 보여주는데, 두 포즈의 다리 배치가 거의 같다(둘 다 오른발이 앞). 그래서 보폭이 아니라 제자리 떨림으로 보인다.
- **원인:** 포즈 시트는 **연기 포즈 모음**이지 **애니메이션 사이클**이 아니다. 달리기 사이클에는 접지 → 통과 → 반대발 접지 같은 연속 프레임이 필요한데, 시트에는 없다. 2D 카드는 그 사이 동작을 만들어낼 수 없다.
- **예상:** 부분적으로 예상했다. 움직임 ★★와 "뚝뚝 끊김"은 예측했다. 다만 두 포즈가 이렇게 비슷해서 사이클 자체가 성립하지 않을 정도라는 것은 에셋을 잘라 본 뒤에야 알았다. 호랑이(t_3 뻗음 ↔ t_4 웅크림)는 차이가 커서 훨씬 낫다.
- **의미:** Three.js의 한계가 아니다. 입력 에셋의 한계다. 사이클용 시트(같은 각도로 8프레임, 접지와 통과를 교대로)를 따로 생성하면 상당히 나아진다. 하지만 그래도 "그림 바꿔 끼우기" 수준이다.

### F2. 포즈가 바뀌는 순간 "툭" 튄다 — 심각도: 중간
- **현상:**
  - 할머니가 g_2에서 g_4(뒤돌아보기)로 한 프레임 만에 바뀐다.
  - 호랑이는 t_3와 t_4가 바뀔 때마다 실루엣과 부피가 점프한다 (6.0~6.23초).
- **원인:** 카드 교체에는 보간이 없다. 포즈 이미지마다 프레이밍과 몸의 비율이 조금씩 달라서 발을 기준으로 맞춰도 몸통이 튄다. 애니메이션 원칙인 "예비 동작 → 새 표정 → 안착"을 넣을 재료가 없다.
- **예상:** 예상했다 ("포즈 교체라 끊김").
- **의미:** 2D 컷아웃의 구조적 한계다. 크로스페이드로 조금 완화할 수 있지만 겹친 잔상이 생긴다. 보간이 되는 3D 리그가 있어야 해결된다.

### F3. 발이 땅에 붙지 않는다, 산길을 벗어난다 — 심각도: 중간
- **현상:**
  - 위치는 등속으로 이동하고, 발 교체 타이밍과 맞물리지 않아 미끄러져 보인다.
  - 4.5초에 호랑이 앞발이 산길이 아닌 이끼 바위 위에 있다.
  - 접지 그림자가 거의 보이지 않는다.
- **원인:**
  - 이 장면에는 3D 지형이 없다. 지면은 "그림의 몇 번째 줄이면 깊이가 얼마"라는 1차원 곡선(수동 샘플)일 뿐이다.
  - 이동 경로는 굽은 산길이 아니라 직선 키 몇 개로 넣었다.
  - 그림자는 평면 카드에 깔리지만, 배경은 깊이 메시라 바닥 면이 고르지 않다.
- **예상:** 미끄러짐은 예상했다. 경로 이탈은 **예상하지 못했다** (경로 키를 산길 곡선에 맞추지 않은 내 설정 실수).
- **의미:** 경로 이탈은 고칠 수 있다 (산길 중심선을 따라 키를 더 촘촘히 넣기). 미끄러짐은 보폭과 이동 속도를 맞추면 줄어든다. 하지만 사이클 재료가 없어서(F1) 근본 해결은 안 된다.

### F4. 깊이 추정의 한계 — 심각도: 중간
- **현상과 대응:**
  - 왼쪽 소나무 줄기가 앞쪽 레이어로 분리되지 않아, 호랑이 등장 위치를 덤불 뒤로 바꿨다.
  - 산길과 원경의 깊이 차가 0.09~0.29로 압축돼 나와서 변환식을 손으로 바꿨다.
  - 카메라가 움직이면 그림 바깥 검은 영역이 드러나 배경을 15% 거울 반사로 연장했다.
- **원인:** 단일 이미지 깊이 추정은 **보이는 표면의 대략적인 순서**만 알려준다. 가려진 뒤쪽 정보는 없다. 그래서 카메라를 크게 움직이면 늘어나거나 뚫린 곳이 보인다.
- **예상:** 예상했다. 그래서 카메라 이동을 작게 제한하는 구도로 설계했다.
- **의미:** A안의 카메라 자유도는 원본 시점 근처 **아주 작은 범위**(이동 약 0.4 유닛, 화각 변화 정도)로 묶인다. 이것도 Three.js가 아니라 재료의 한계다.

### F5. 캐릭터와 장면의 조명·공간 통합 — 심각도: 낮음 (이번 장면에서만)
- **현상:** 캐릭터 카드는 조명을 받지 않고, 그림에 그려진 빛을 그대로 쓴다. 대기 원근(안개, 거리감)의 영향도 받지 않는다.
- **원인:** 평면 카드에는 법선과 부피가 없어서 다시 조명할 수 없다.
- **예상:** 예상했다.
- **의미:** 이번에는 캐릭터 시트와 배경이 모두 같은 노을빛으로 그려져 있어서 **운 좋게** 티가 덜 났다. 조명이 다른 장면이면 바로 어긋난다.

### F6. 카메라를 돌릴 수 없다 — 심각도: 높음 (테스트 목적 기준)
- **현상:** 모든 샷이 정면 또는 3/4 각도로 고정됐다. 캐릭터 주위를 도는 샷, 옆이나 뒤에서 보는 샷은 불가능하다.
- **원인:** 캐릭터가 평면 카드라 옆에서 보면 두께가 0이다.
- **예상:** 예상했다. 그래서 컷 구성을 처음부터 이 약점을 피하게 짰다.
- **의미:** "3D 애니메이션"의 핵심인 카메라 자유도가 없다. 즉 **A안은 3D 애니메이션이 아니라 "깊이감 있는 2D 합성"**이다.

### F7. 클로즈업 해상도 — 심각도: 낮음 (720p 기준)
- **현상:** S5에서 호랑이가 화면을 채울 때 털 디테일이 뭉개진다 (9.25초 크롭).
- **원인:** 포즈 시트의 한 칸은 512px이다. 이를 2배 업스케일한 텍스처를 다시 3~4배 확대했다.
- **예상:** 예상했다.
- **의미:** 720p에서는 견딜 만하다. 1080p였으면 확연히 보였을 것이다. 고해상도 개별 포즈 이미지가 있으면 해결된다.

### F8. 표정과 입 연기 불가 — 심각도: 중간
- **현상:** 호랑이 대사 구간에 맞춘 입 뻐끔거림을 계획했지만 포기했다. 표정은 포즈 이미지에 박힌 것 하나뿐이다.
- **원인:** 달리기 포즈가 전부 입을 벌린 상태라, 입만 바꿀 방법이 없다 (몸 전체를 바꿔야 함).
- **예상:** 예상했다 ("립싱크 불가").
- **의미:** 대사가 있는 캐릭터 연기는 A안으로 불가능하다.

### F9. 오디오 미완성 — Three.js와 무관
- **현상:** 대사와 BGM을 만들지 못했다. 효과음 7개는 만들었지만 사용하지 않았다.
- **원인:** 모바일 앱에서 API 키 보안 입력 폼이 표시되지 않아 키를 전달할 경로가 없었다. 이후 사용자 결정으로 범위에서 뺐다.
- **의미:** Three.js 테스트 결과에는 영향이 없다. 다만 **모바일 환경에서 외부 API 키가 필요한 작업은 시작 전에 키 전달 경로부터 확인해야 한다**는 교훈이 남았다.

## 5. "예상대로"의 의미

1. **예측이 맞았다는 것은 A안이 "실패한 방식"이라는 뜻이 아니다. 한계를 미리 정확히 짚었다는 뜻이다.** 기획 단계 비교표의 예측은 이랬다.
   - 정지 화면 ★★★★: 맞았다. 스냅샷은 원본 룩 그대로다.
   - 움직임 ★★: 맞았다. F1, F2, F3.
   - "카메라가 캐릭터를 돌아볼 수 없음": 맞았다. F6.
   - "테스트로서의 의미 낮음 (이미지 합성 테스트가 됨)": 맞았다.
2. **실패의 원인이 Three.js 쪽이 아니라 에셋 쪽에 몰려 있다.** 실패 9개 중 7개(F1~F8)는 "2D 이미지에 다른 각도, 중간 동작, 가려진 뒤쪽, 부피 정보가 없다"는 같은 뿌리에서 나왔다. Three.js가 맡은 렌더링, 타이밍, 결정성, 후보정은 실패 목록에 없다.
3. **그러므로 이번 결과로 "Three.js로 만족할 만한 3D 애니메이션이 되는가?"에 답할 수 없다.** A안이 증명한 것은 "Three.js는 영상 렌더 엔진으로 믿을 만하다"까지다. 캐릭터 애니메이션 품질은 **B2안(실제 3D 모델과 리그)**에서 처음으로 Three.js의 몫으로 측정된다.
4. **예상하지 못한 실패는 고칠 수 있다.**

| 실패 | 성격 | 추가 작업으로 개선? |
|---|---|---|
| F1 할머니 사이클 | 에셋 (시트가 사이클용이 아님) | 부분 개선 — 사이클 전용 8프레임 시트 생성 |
| F2 포즈 팝 | **구조적** (카드 교체) | 거의 불가 |
| F3 경로 이탈 | 설정 실수 | **가능** — 산길 곡선 키 |
| F3 발 미끄러짐 | 구조적 + 에셋 | 부분 개선 — 보폭과 속도 맞추기 |
| F4 깊이 한계 | **구조적** (단일 이미지) | 불가 — 카메라 이동 제한으로 회피 |
| F5 조명 통합 | **구조적** | 불가 (같은 조명 그림일 때만 성립) |
| F6 카메라 각도 | **구조적** | 불가 |
| F7 해상도 | 에셋 | 가능 — 고해상도 포즈 |
| F8 표정·입 | **구조적** | 불가 |
| F9 오디오 | 환경 (키 전달 경로) | 범위 외 |

## 6. B2안과 힉스필드 비교에서 볼 점

- **B2안에서 Three.js에게 직접 물어볼 질문:**
  - 코드로 만든 캐릭터가 부드러운 보간, 연속 사이클, 카메라 회전을 갖췄을 때 "봐줄 만한가"?
  - 툰 셰이딩과 림 라이트로 3D 애니메이션 풍 룩이 어디까지 나오나?
  - 털(호랑이)과 천(치마)을 어떻게 근사할 수 있나? Three.js 실시간 렌더의 약점이 여기서 처음 드러날 것이다.
  - 렌더 속도: A안은 프레임당 0.87초. B2는 셰이딩이 무거워지면 늘어날 것이다.
- **배경은 A안의 깊이 메시를 B2에서도 재사용할 수 있다.** 캐릭터만 3D로 바꾸는 하이브리드가 B2의 현실적인 형태다.
- **힉스필드(AI 영상)와 비교할 축:**

| 축 | Three.js |
|---|---|
| 정밀 제어 (타이밍·구도를 프레임 단위로) | 압승 |
| 재현성 (같은 입력 → 같은 영상) | 압승 |
| 캐릭터 연기·털·천의 자연스러움 | A안에서는 열세가 확실. B2 결과로 판정 |
